# Step 9: safety and limits

Status: **done** (10 November 2026; checked in game). Plan: [PLAN.md](../PLAN.md), step 9.

## The items of the plan

1. **Escape path: done in step 6** (per message, owner, 7 November 2026): a message coded larger than 1 KB is also coded with its fields raw and the smaller is sent, so the worst case (every field of every entity random) is 0.996 to 0.998 of a raw layout from 64 entities on, for 1 to 1,023 entities ([step-06-cpp-codec.md](step-06-cpp-codec.md), part D). `netcodec.synthetic` checks it on every build: about 250 of its 100,100 messages are escaped, up to 52,520 bytes. This is also the plan's worst-case check (it said 1,000 entities: a snapshot holds at most 256, `MAX_SNAPSHOT_ENTITIES`; a gamestate's baselines up to 1,023).
2. **Size cap: done** (owner's choices, 10 November 2026). A message that does not fit in `MAX_MSGLEN` (49,152 bytes, the largest the netchan reassembles) was sent empty, as the legacy code cleared an overflowed message: the client then decoded nothing and asked for a full snapshot, larger still; a gamestate left the client waiting on its loading screen. Now (`codemp/server/sv_netcodec.cpp`):
   - **Snapshot**: coded again with only the entities nearest to the player (`SV_NetcodecFitSnapshot`, distance of `pos.trBase` to the player's origin), as many as fit, found by a binary search over their count (about ten codings, only when a message overflows; no cost otherwise). The frame's entities, which only this message uses, are rewritten in place in the shared ring, so the frame stays the base of the next messages; the entities left out are absent from this snapshot only and come back in the next ones, coded against their baseline. A warning gives the counts, and `svnetstats` counts the snapshots cut to fit. If not even the player state and the commands fit, the message still goes out empty, with a warning.
   - **Gamestate**: the client cannot play without it, so it is dropped (`SV_DropClient`, "gamestate too large for a message"). The reason travels as the `disconnect` server command, but the client executed server commands only once cgame runs (`CL_GetServerCommand`), so a client dropped while connecting or loading kept waiting for its gamestate, the server sending to its dropped slot (as in OpenJK, for a kick during the connection too). `CL_ParseCommandString` now handles a `disconnect` before cgame runs as `CL_GetServerCommand` does: the client returns to the menu, which shows "Server disconnected" and the reason.
   - **`sv_netcodecMaxBytes`** (debug, 0 by default): the largest message the server codes, below `MAX_MSGLEN`, to test both paths in game; real messages are far from the limit (the largest held-out message is 556 bytes, a gamestate about 4 KB).
3. **Fuzz corpus and sanitizer builds in a CI: not done** (owner, 10 November 2026): the validations stay on the owner's VMs (`validate.sh`, `validate.bat`: ASan + UBSan presets on GCC and MSVC, the malformed-input tests of both decoders in every preset). The libFuzzer targets and their committed corpora (`fuzz/corpus`, `fuzz/corpus_client`) are run by hand here.
4. Done in step 8 part 4: the client packet decoder bounds what a packet can make the server decode (client command texts of at most 1,023 characters), tested with malformed packets and a fuzzer.

## Check in game (owner, 10 November 2026, MSVC x64 client and server)

1. `sv_netcodecMaxBytes 1000` on the server, then connect: the gamestate (about 4 KB) does not fit, the server prints the warning and drops the client, which returns to the menu with "Server disconnected" and "gamestate too large for a message". Then `sv_netcodecMaxBytes 0` and connect normally. (First try, owner: the client stayed on "Awaiting gamestate", the reason only in its console, an out-of-band `print`; hence the client change above.)
   Result: the client returns to the menu with the reason.
2. In game with bots, `sv_netcodecMaxBytes 200`, then 100 for a few seconds: snapshots larger than the limit are cut (distant players and objects disappear for a message and come back), `svnetstats` counts them ("cut to fit"), `netstats` shows no message not decoded. Then `sv_netcodecMaxBytes 0`.
   Result: 1,779 messages (83.3 bytes per message), 296 cut to fit, every snapshot coded against the previous message (a cut frame is a valid base for the next one); the client: 1,988 messages, 0 lost, 0 not decoded; 5,561 client packets, 0 not decoded.

The VM validations ran before the last two changes (the snapshot cut and the gamestate drop were validated; the client's `disconnect` handling and the removal of the out-of-band `print` came after, engine files only, built with clang and MSVC).
