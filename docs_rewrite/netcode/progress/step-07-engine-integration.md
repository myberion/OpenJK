# Step 7: integration in the engine

Status: **in progress** (started 8 November 2026). Plan: [PLAN.md](../PLAN.md), step 7.

## Decisions (owner, 8 November 2026)

- The codec replaces the server-to-client format in the branch's build, with no switch; the comparison is the reference build (`E:\Jeux\Jedi Academy default - openjk`, frozen at commit `3f50d242d`, see "Test setup"). The protocol number, the handshake and any coexistence of protocols 26 and 27 are decided at the end of the plan (7 November 2026), so until then a reference client and a branch server (or the reverse) are not refused at connection and do not understand each other.
- The netchan obfuscation XOR is dropped on server-to-client messages (`SV_Netchan_Encode`, `CL_Netchan_Decode` removed): its key was chosen on the client from the reliable acknowledge read in clear at the start of the message, which the codec now codes. To revisit in plan step 11 (restore an equivalent, replace it by the encryption, or leave it out). The client-to-server direction keeps it.
- A debug cvar on the server, `sv_netcodecCompare`, also codes each message in the legacy format (huffman bitstream, `msg.cpp`) and prints the byte ratio (1: every 10 seconds, 2: every message); it works with bots, where step 5's demos are not comparable.
- UDP downloads carry one block per message (see "Known limits"); to fix in plan step 9, possibly with a download system of their own.

## Parts

1. **Server (done 8 November 2026).** `codemp/server/sv_netcodec.cpp`: every server-to-client message is a `netcodec::engine::ServerMessage` coded by one `ServerCodec` (scratch buffers only) and sent as the packet's payload (no huffman, no `svc_EOF`, no XOR: `SV_Netchan_Transmit`). Each client has one `netcodec::engine::Frame` per message slot (`PACKET_BACKUP`), reset at connection and with each gamestate (the client clears its state then). Messages: the gamestate (`SV_SendClientGameState`), the map change (`SV_SendClientMapChange`), and the snapshot message (`SV_SendClientSnapshot`: the server commands not yet acknowledged, the game dir that was a separate `svc_setgame` message before, the snapshot coded against the base `SV_SnapshotBase` selects as before, and a download block). `SV_WriteSnapshotToClient` (legacy format) and `SV_CreateClientGameStateMessage` stay for `sv_netcodecCompare`. `MAX_RELIABLE_COMMANDS` is 256 (the codec codes the server commands against earlier ones and needs both sides to keep 256). `sv_padPackets` is removed (it padded only the legacy format, which is no longer sent), as are `SV_ENCODE_START` and `CL_DECODE_START` (the offsets of the removed XOR).
   Reviewed again on 8 November 2026, no defect found: every server-to-client send goes through the codec (`SV_FinalMessage` too, through `SV_SendClientSnapshot`). Every chain of deltas starts from a full snapshot: the frames are reset at connection and with each gamestate, a client that is not `CS_ACTIVE` gets no base, and a bot's slot, which is not reset when the bot is allocated, has its frames reset when it starts recording (part 3), so stale frames are never reached. The server's acknowledge check (`reliableAcknowledge` at least `reliableSequence - MAX_RELIABLE_COMMANDS`) keeps every command to send in the ring; the commands the client holds come from the acknowledged base's record, not from the acknowledge the client sends. The client keeps its commands sanitised (`%` becomes `.`) while the server codes against the raw texts: this does not desynchronise the decoder, since token boundaries and the number test are the same for both characters, and a token copied from the reference comes out sanitised as before.
2. **Client (done 8 November 2026).** `codemp/client/cl_netcodec.cpp`: `CL_ParseServerMessage` decodes with one `ClientCodec`; the entities are written into `cl.parseEntities` in place, the player states into a temporary snapshot, the gamestate's baselines into a table of the codec's own (copied to `cl.entityBaselines` once the gamestate has cleared the client state). The `CL_Parse*` functions of `cl_parse.cpp` now take the decoded values (commands, gamestate begin / config strings / end, set game, snapshot, download) and apply them as before; the legacy message reader is gone. Strings keep the legacy sanitation (`%` becomes `.`). A message the client cannot decode (malformed, or coded against a snapshot it no longer holds) is dropped whole; the next packet then asks for a full snapshot (`clc_moveNoDelta`), and the reliable commands are sent again until acknowledged. A slot whose entities the next message may overwrite in `cl.parseEntities` stops being a base. The codec's frames are reset with the client state (`CL_ClearState`). `cl_shownet 1` prints the size of each packet as before; `cl_shownet 2` prints one line per decoded operation (each server command with its text, the gamestate and its config strings, the game dir, the snapshot with its delta and entity count, the download block, the map change) and "not decoded" for a dropped message; the per-field output of levels 4, -1 and -2 is gone (the codec keeps no per-field trace).
   Reviewed again on 8 November 2026, no defect found: the operations are applied in the legacy order; the decoder clears the whole baseline table before it fills a gamestate, so no baseline of the previous map remains; the slots whose entities the next message may overwrite are invalidated before each decode, so even a decode that fails midway overwrites no base still in use; a lost message, or a decoded one without a snapshot, never leaves a usable slot; a command the server codes against is always in the client's ring, since the server uses it only while it is newer than `reliableSequence - 256` and the client is never ahead of the server. A message the client cannot decode is dropped whole, where the legacy reader still applied its commands and download block when only the snapshot's base was missing: the commands are sent again until acknowledged, and the game dir and download blocks only travel in messages without a base, which always decode. The download block number is read as 16 unsigned bits (the legacy reader read it signed, so files above 64 MB failed).
3. **Demos (done 8 November 2026; checked in game, see "Results").** A demo is played back by the normal decoder from an empty state, so every message in it may refer only to what the demo holds: its base, its base's own base, and the server commands it is coded against (up to `kCommandWindow`, 127, commands back, now in `engine.h`). The legacy demo rules (`demowaiting`, `minDeltaFrame`, the full snapshot the client asked of the server when it started recording) are gone; the codec's frames do their work.
   - Server demos (`svrecord`, `sv_autoDemo`): the demo is a copy of the messages sent, as before, since the server records every message it sends and the client's packets arrive in order. `SV_RecordDemo` resets the client's codec frames and writes a gamestate coded by the codec (`SV_NetcodecDemoGameState`) holding the commands from `kCommandWindow` before the first one a later message can carry (the client's acknowledge plus one) to the last. After the reset the codec finds no base, so the next message is coded without one, and the later messages only against messages coded since, which are in the demo, as are their own bases. Cost: none with `sv_autoDemo`, whose demos start with the full snapshot sent when the client enters the game; a `svrecord` in the middle of a game sends full snapshots for about one round trip, until the client acknowledges a message of the demo, as the legacy rules did.
   - Client demos (`record`): the network messages refer to bases and commands from before the recording, and a message the client could not decode, or a full snapshot the server sent before it saw the client's request, would leave holes. So the demo is a coded stream of its own: each message the client decodes is coded again by a second `ServerCodec` against the previous snapshot of the demo, with the commands it brought (each command written once) and without its download block (`CL_NetcodecDemoRecord`); `CL_Record_f` writes a gamestate coded from the client's state with the last 127 commands (`CL_NetcodecRecordGameState`). The demo's frames are reset at `record` and with each gamestate. Cost: one more coding per message on the player's machine (about 1.5 µs, 0.006 % of a core at 40 messages per second); nothing is asked of the server. `CL_WriteDemoMessage` (the raw copy) and the legacy gamestate writer are gone, and with them the two `MSG_CheckNETFPSFOverrides` calls of `CL_ParseSetGame` (on the client they only fed the field tables of `msg.cpp`).
   - Demos of the legacy format (protocol 26 files of the reference build or of other games) cannot be played back; whether to keep a reader or a converter is decided with the protocol number at the end of the plan.
4. **Part F decisions (to do).** Missile roundings removed; `pmove_float`, `pmove_fixed`, `pmove_msec` removed.
5. **Statistics and tests (to do).** Counters (bytes per snapshot, escapes, base age); tests on the loopback, over UDP with `net_dropsim`, and with a GCC server on the Debian VM.

## Results

- Dedicated server built with clang (llvm-mingw), 6 bots, server demos of the bots (so that their messages are coded), about 70 seconds, `sv_netcodecCompare 1`: no message refused by the codec; 15.1 to 32.0 bytes per message against 38.2 to 78.8 in the legacy format, ratio 0.396 to 0.418 over 10-second windows (step 6, demos: 0.381 to 0.483). (Run under `lldb`: the dedicated server's Windows console crashes at start when its input is a pipe, which is not the codec.)
- MSVC x64 client and dedicated server on the Windows host, bots, `cl_shownet 1` and `cg_showmiss 1`, against the reference build played the same way: packets of 80 to 270 bytes in combat (about 150) and 30 to 60 when dead, against 250 to 540 (about 330) for the reference, about 0.45 of the size; prediction misses of 0.1 to 3.0 units against 0.2 to 2.4: of the same order. (`cl_shownet 1` printed the payload without the 4-byte netchan header on that build; it now prints the whole packet, as the reference does.) `WARNING: double event` and `PredictionTeleport` at respawn with `cg_showmiss 1` appear in the reference build too: the base cgame's own behaviour.
- `map_restart` with `developer 1` and `cg_showmiss 1`, both builds: the same server commands in the same order, no message refused by the codec. The reference prints a long run of `exceeded PACKET_BACKUP on commands` (the cgame freezes the prediction while the newest snapshot is older than the 64 user commands it keeps) and the branch none; likely cause, not checked: right after the restart the server sends a burst of config-string commands, which in the legacy format makes large messages held back by the rate (`sv_clientRate` 25000), while the codec's are about 2.5 times smaller (to confirm: `rate 90000` on the reference client should make the messages disappear). A first branch run showed one prediction miss of 796 units after the restart's respawns; not seen again in the next runs.
- Server demos (part 3), clang dedicated server, 4 bots, checked with a small decoder that plays each demo from an empty state as the client does (local tool, not committed): the `sv_autoDemo` demos of two maps (6 files, 105 to 393 messages each, one gamestate each) and a `svrecord` demo of a bot across a `map_restart` and a `map` (934 messages, 2 gamestates, 927 snapshots, 60 new commands): 0 messages not decoded. The demos still open when the server quits have no end marker (the server does not close them at shutdown, as before); the client's player stops at the end of such a file ("Demo file was truncated").
- Demos (part 3), MSVC x64 client and dedicated server, owner: a client demo with deaths and respawns, a client demo recorded across a `map_restart`, a `svrecord` demo started in the middle of a game and recorded across a `map_restart`, and `sv_autoDemo` demos of the player and of bots all play back correctly. With `developer 1`, `sequenced packet without connection` is printed for about the `sv_zombietime` after `demo` (the server still sends to the client it has just dropped, as in the reference build).

## Known limits

- Demos of the legacy format cannot be played back (part 3; decided with the protocol number at the end of the plan).
- UDP downloads: one 2,048-byte block per message. The legacy format sent `(rate * snapshotMsec / 1000 + 2048) / 2048` blocks per message (up to the 8-block window): also one block at the branch's defaults (`sv_clientRate` 25000, 50 ms between snapshots), more only from a rate of 40,960 bytes per second at 50 ms. On a LAN (`sv_lanForceRate`, rate 100000, a message every server frame) it sent 3 blocks per message, so downloads there are about 3 times slower. Plan step 9.
- A reference client and a branch server do not understand each other and are not refused (end of the plan).
