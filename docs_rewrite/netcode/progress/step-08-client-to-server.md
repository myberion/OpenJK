# Step 8: client-to-server messages by the codec

Status: **done** (9 to 10 November 2026; parts 3 and 4 done 10 November 2026: the engine codes and decodes the client packets with netcodec, checked in game on the loopback and on the VPS; the decoder holds against malformed input). Plan: [PLAN.md](../PLAN.md), step 8.

## Why recordings, and where

The demos hold only what the server sends to the client, never the client's packets (user commands, acknowledges, client commands), so the client-to-server direction has no corpus yet. The server records them instead, and an offline tool measures them, as the demo traces and `netcodec_bench_size` / `netcodec_bench_codec` did for the other direction.

The recordings come from a dedicated server reached over the Internet (owner, 9 November 2026: the VPS), not from a local game: on the loopback the client sends a packet every frame with one user command (`CL_ReadyToSendPacket`, `codemp/client/cl_input.cpp`), and on a LAN too while `cl_lanForcePackets` is 1, whereas over the Internet `cl_maxpackets` (63) caps the packets, so each carries several commands plus the previous packet's (`cl_packetdup`), with a real acknowledge delay. Bots send no packets: only the human players' packets are recorded; bots are there for combat and varied input.

Wanted in the corpus: several separate sessions (one is kept out of training), several `com_maxfps` (60, 125, 333: the number of user commands per packet changes), combat and movement, some chat and commands (`team`, votes).

## Parts

1. **Recorder and reader (done 9 November 2026; corpus of six sessions recorded, see "Results"; the recorder was removed with part 3, owner, 10 November 2026: its files held legacy packets, and a recorder for retraining comes back with plan step 13).**
   - `sv_recordClientPackets 1` (debug, server, `codemp/server/sv_netcodec.cpp`, removed in part 3): each client's packets are written as `SV_ExecuteClientMessage` reads them, that is after the netchan header and with the obfuscation XOR already removed, to `clientpackets/client<n>_<date>.jkcp` under the home path, one file per connection (closed when the client drops, when the cvar is set back to 0 or when the server shuts down). File: a header (`JKCP`, version 1, record size), then per packet a record and the packet's bytes. The record holds `sv.time` and `Sys_Milliseconds()` at arrival, the user-command key the server derives for the packet (`SV_UserMove`), so that the packet decodes offline, and the acknowledged snapshot's server time and the player-state fields that match user-command fields (`commandTime`, `viewangles`, `delta_angles`, `weapon`, `fd.forcePowerSelected`, `stats[STAT_HOLDABLE_ITEM]`; server time -1 when the server no longer holds that snapshot): the bases a coded format can use besides the previous command.
   - `netcodec_bench_client` (`codemp/netcodec/bench/bench_client.cpp`): decodes every packet as the server does, with OpenJK's own `msg.cpp` (glue in `bench/legacy/legacy_codec.cpp`: `DecodeClientPacket`, following `SV_ExecuteClientMessage`, `SV_ClientCommand`, `SV_UserMove`), codes it again as the client does (`EncodeClientPacket`, following `CL_WritePacket` and the `clc_EOF` of `CL_Netchan_Transmit`) and checks that the bytes holding bits are identical; it prints, per file and in all, the packets per second, the bytes per packet and per second, how they split between the acknowledges, the client commands and the user commands, the user commands per packet (and how many are new rather than repeated from the previous packets), the client commands, and how often the acknowledged snapshot was known. It exits with 1 if a packet does not decode or codes again differently.
2. **Format in the library (done 10 November 2026, validated on every compiler, timed on four; the engine interface comes with part 3).** Designed from the measurements of part 1 (`tools/python/client_fields.py`, candidate "planned format": 8.15 ideal bytes per packet on the held-out session) and the decisions of 9 November 2026 ([README.md](README.md), "Decisions"):
   - `src/client_codec.cpp`, interface in `include/netcodec/codec.h` (`ClientPacket`, `ClientBase`, `ClientPacketEncoder`, `DecodeClientPacket`, `ClientBaseLookup`, `CountClientPacket`). A packet decodes alone. In order: the acknowledged message as its low 8 bits (the server takes the nearest number at or below its last message sent); a flag saying whether the user commands are coded against the acknowledged message, which both sides then hold (the client codes without it when it no longer holds it or its last message is too old); with it, `serverId` as "the same as that message's" (else raw) and the server command acknowledge against that message's `cmdSeq`, without it both raw; the client commands (count, first sequence number against the one after that message's `ack`, texts with the server command text contexts); the move operation; the user-command count; per user command, the time (the first against the base player state's `commandTime`, the others as a step given the previous step, escaped from 63 ms), the three view angles as 16-bit differences from the previous command (the first from the base's view angle index less `delta_angles`) given the previous difference, and nine bytes (buttons low and high, weapon, forcesel, invensel, generic_cmd, forwardmove, rightmove, upmove) given the previous command's value, with separate tables for the first command (based on the snapshot's weapon, selected force power and holdable item). As in the legacy format the angles and the buttons travel as 16 bits; the other fields are exact (the legacy reader turned a move of -128 into -127).
   - The server-to-client messages now carry `serverId` (`Message::serverId`, `HeaderRecord::serverId`, `engine::ServerMessage::serverId`, `engine::Record::serverId`, `engine::ClientMessage::serverId`; the server sets `sv.serverId`, client demos copy the decoded one): one flag symbol against the base, raw when it changes or without a base. The server tables were retrained: only the new context differs (`jka_tables.inc`, 1,296 trained contexts); round-trip hash `0xB752DA538DCD4AA6`, synthetic `0x88B36A2A82916952`.
   - Contexts appended after the server ones (`src/contexts.h`, `ClientScalar`, `ClientStep`, `ClientAngle`, `ClientField`), so that the server context numbers do not move; client tables in their own generated file, `src/generated/jka_client_tables.inc` (143 trained contexts, 19,978 frequencies), written by `netcodec_train_client` (`tools/train_client.cpp`; `tools/write_tables.h` is now shared with `netcodec_train`) from the client traces of sessions A to E. The validation scripts check that the x86 client trainer writes the committed table unchanged.
   - Client traces (`test/client_trace.h`): `netcodec_bench_client --trace` writes the decoded packets with their bases (`data/traces/client_train.bin` for A to E, `client_holdout.bin` for F; not committed). The recording holds the acknowledged snapshot's fields but not its record: its `cmdSeq`, `ack` and `serverId` are approximated (the previous packet's `reliableAck` and `serverId`, the last client command sequence before the packet); exact in the engine, they only weigh on rare symbols.
   - Tests (`test/test_client.cpp`): `netcodec.client_synthetic` (100,000 random packets on every path: with and without base, serverId changed, client commands, steps beyond the escape, any angle and byte; hash `0xCFE7E7FEB2FB9F06`) and `netcodec.client_roundtrip` (each traced packet against its base when the recording had it, then again without a base: 163,578 codings; hash `0xC371DB108DA14F6D`). Same hashes with clang x64 and x86; clang-tidy clean.
   - The engine checks the offsets the codec reads (`playerState_t` and `usercmd_t`, `codemp/server/sv_netcodec.cpp`).

## Part 3: what was done

The model is step 7: a small C++11 interface in `engine.h`, the conversions in `src/engine.cpp`, the engine glue in `sv_netcodec.cpp` and `cl_netcodec.cpp`.

1. **Base window (owner, 10 November 2026).** A packet coded against the acknowledged message can only be decoded while the server still holds that message's values; otherwise the packet is dropped, user commands included. With the 32 frames of step 7 (`PACKET_BACKUP`), every packet of a client more than 32 messages behind would be dropped (a lag spike of 1.6 s at `sv_fps` 20, 0.8 s at 40), and the frames are also reset with each gamestate and at the start of a server demo (`sv_autoDemo` when the player enters, `svrecord`). So the server keeps, per client, the values a packet is coded against for each of its last 256 messages (`kAckWindow`, the window over which the 8-bit acknowledge is read without ambiguity): 32 bytes each, 8 KB per client, 256 KB for 32 clients, reset only at connection. Compared with reading them from the frame's `playerState_t` at each packet, the work moves from each packet received (63 per second) to each message sent (20 per second) and reads one cache line instead of five.
2. **Library.** `ClientBase` (`codec.h`) now holds the values themselves (serverId, cmdSeq, ack, commandTime, the three angle indices less `delta_angles`, the low bytes of weapon, selected force power and holdable item), computed by `ClientBaseOf(header, ps)`, the only extraction, used by the engine, the tests, the benchmark and the trainer; same format, tables and hashes. `engine.h`: `PacketBase` (the same values with the message number, -1 for none), `PacketBaseOf(frame)`, `Move`, `ClientPacket` (serverId, the acknowledges, the client commands as `Command`, the move, the `usercmd_t` images), `ClientCodec::EncodePacket(packet, base, out, size)` and `ServerCodec::DecodePacket(bytes, size, latest, bases, packet)`; a decoded packet points into the codec until the next decode.
3. **Client** (`CL_WritePacket`, `cl_input.cpp`; `CL_NetcodecWritePacket`, `cl_netcodec.cpp`): the same values as before (`cl.serverId`, `clc.serverMessageSequence`, `clc.serverCommandSequence`, the client commands not yet acknowledged, the move type and the user commands, `cl_packetdup` unchanged) coded into the payload; `CL_Netchan_Transmit` sends it without `clc_EOF` and without the XOR (`CL_Netchan_Encode` and `CL_ENCODE_START` removed). The base rule: the packet is coded against the acknowledged message when the client holds its snapshot and (time since that message arrived + round-trip time) × messages per millisecond < 128, half the window. The time between messages is the snapshot time of the message less that of its own base, over their distance; the round-trip time is measured as the legacy client's ping (from the sending of the newest packet whose last user command the snapshot's `commandTime` covers to the message's arrival), but over the last 256 packets the client keeps (`s_sent`) rather than the 32 of `cl.outPackets`. When either is unknown (no base snapshot, right after a gamestate, or no such packet), the packet is coded without a base.
4. **Server** (`SV_ExecuteClientMessage`, `sv_client.cpp`; `SV_NetcodecDecodeClientPacket`, `sv_netcodec.cpp`): `SV_Netchan_Process` no longer removes a XOR (`SV_Netchan_Decode` and `SV_DECODE_START` removed); the payload is decoded with `latest` = `netchan.outgoingSequence - 1` against the client's 256 `PacketBase`s, which `SV_NetcodecSend` sets for each message with a snapshot (and clears for the others); a packet that does not decode is dropped. The same logic as before then runs on the decoded values: the `messageAcknowledge` and `reliableAcknowledge` checks, the `serverId` checks, each client command through `SV_ClientCommand` (flood protection unchanged; the text bounded to 1,023 characters, `%` made `.` as the legacy string reader did), and the user commands through `SV_UserMove` (copied from the decoded packet; the `sv_legacyFixes` clamps unchanged; the key is gone).
5. **Ping** (decided 9 November 2026): `messageSent` is the real time (`Sys_Milliseconds`) at sending; `messageAcked` the real time of the first packet acknowledging the message, with an explicit `acked` flag instead of the -1 time, and only while the frame still holds the message (the slot of a message being sent in fragments is excluded); `SV_CalcPings` reads the flag.
6. **`sv_netcodecCompare`** also codes each decoded client packet in the legacy format (`MSG_WriteDeltaUsercmdKey` with the key) and prints its byte ratio, with the same period as the messages (the printing is shared, `SV_NetcodecCompareAdd`).
7. **Statistics**: `svnetstats` adds per client the packets received, bytes per packet and packets not decoded; `netstats` the packets sent, bytes per packet and packets coded without a base.
8. **Recorder** removed (owner, 10 November 2026): `sv_recordClientPackets` and its file writer. `netcodec_bench_client` still reads the part 1 files and describes their format.
9. **Test**: `netcodec.client_roundtrip` also passes every traced packet through `engine.h` (`PacketBaseOf` a frame holding the traced values, the server's window, `EncodePacket`, `DecodePacket`): 163,578 codings, the same bytes as the library, the same packet back, and a packet coded against a base is refused once its slot holds a later message.

## Part 4: results

The server decodes the packets of anyone, so its decoder must hold against any input: return without fault, bound what it builds, and accept only what the encoder can code.

1. **Text length limit.** A client command's text was decoded up to the generic 65,536 characters, 256 commands per packet. Measured (a scratch tool on the release library): the most compressible text (one character repeated, `@`) costs 12.5 characters per byte, so 256 commands of 65,535 characters decode in 54 ms from a 1.3 MB message, and a message of `MAX_MSGLEN` (49,152 bytes, which the netchan reassembles from fragments) in about 25 ms: a cheap way to load a server. A client holds each command in a buffer of `MAX_STRING_CHARS` (so at most 1,023 characters), and the server truncated longer texts anyway (`SV_ClientCommand`; the legacy reader read at most 1,024 characters per string), so the decoder now refuses a packet holding a longer command (`kMaxClientCommandLength`, 1,023; `GetCommandText` takes the limit, the server messages keep theirs) and the engine's `EncodePacket` refuses to code one (`engine::kMaxCommandLength`, checked against `MAX_STRING_CHARS - 1` in `cl_netcodec.cpp`). Worst case now: 256 commands of 1,023 characters, about 1 ms of decoding from a 21 KB message. No format change: the same bytes, the same hashes.
2. **Malformed-input test** (`test/test_client_robustness.cpp`, `netcodec.client_robustness`, every preset, so under ASan + UBSan too): 20,000 synthetic packets (`test/client_synthetic.h`, the generator of `netcodec.client_synthetic`, now shared), 20 mutated copies of each (`test/mutate.h`, the mutations of `netcodec.decode_robustness`, now shared: bits flipped, bytes changed, truncated, inserted, deleted, appended, random bytes), each decoded with a random `latest` (near the acknowledge, or anywhere) and one of three lookups (the packet's own base, another base for any message, none). 400,000 malformed inputs decoded without fault; 211,783 accepted, each coded again against the base its decoding used and decoded again to the same packet (0 refused, 0 different); a command of 1,023 characters decodes and one of 1,024 is refused.
3. **libFuzzer target** (`fuzz/fuzz_client.cpp`, `netcodec_fuzz_client`, preset `mingw-clang-fuzz`): a fixed server state (last message sent 1,000; one base, that of a synthetic packet, held for any acknowledged message), the same checks as the test, aborting on any difference. 10 minutes from 256 synthetic seeds (`--write-seeds=<dir>`): 21.1 million inputs (35,000 per second), no fault, no abort, no input slower than 1 s, 591 MB at most. The corpus, minimised with `-merge=1`, is committed in `fuzz/corpus_client` (188 inputs, about 10 KB, binary in `.gitattributes`); both committed corpora replay without fault. Run: `netcodec_fuzz_client -max_len=4096 -timeout=10 -rss_limit_mb=2048 -max_total_time=<s> <work dir> fuzz/corpus_client` (the sanitizer runtime DLLs of llvm-mingw, in `x86_64-w64-mingw32/bin`, must be in the `PATH`).
4. Validated: clang Release, x86, ASan + UBSan, Debug, clang-tidy (nothing reported) here; `validate.sh` (GCC 12 Release, Debug, ASan, x86, Clang 14) and `validate.bat` (MSVC x64 Release and Debug, x86, ASan) all OK, the same figures in every preset; the game built with clang, GCC and MSVC.

- The legacy coder sizes a message as `bit / 8 + 1` bytes (`msg.cpp`), so a packet ending on a byte boundary (12 % here) carries one more byte that nothing writes: on the client, whatever its stack held at that place (obfuscated by the XOR, but sent). The reader compares only the bytes holding bits.
