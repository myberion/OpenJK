# Step 14: fixed simulation tick, lag compensation, and the rest of "beyond the codec"

Status (12 November 2026): part 1 done (the server's CPU time in `svnetstats`, commit `aded85287`; the fixed rate of 200,000 bytes per second); part 2 (game timing) done with a new design (commits `4efd458f0` and `1376279bd`), the game's logic at its 20 Hz pace on a 100 Hz tick, proven identical to `sv_fps` 20 with scripted scenarios (section 9; the working notes, audits and traces are in [step-14-audit-100hz.md](step-14-audit-100hz.md)); parts 3 to 9 to do. The survey, the measurements and the owner's choices that lead here are in [../11-tick-and-lag-compensation-survey.md](../11-tick-and-lag-compensation-survey.md). Paths are relative to `codemp/`.

Owner's choices (11 November 2026): a fixed simulation tick of 125 Hz (revised the same evening: **100 Hz**, so that every 20 Hz instant is a tick, and the game's logic runs at its 20 Hz pace, identical to `sv_fps` 20: section 9) shared by client and server, lag compensation by tick, rate 200,000 bytes per second; designed from recent games rather than from the JKA mods, cleanly and optimised, even if it means starting again from zero; every defect found on the way fixed; the analysis covers the engine (client and dedicated server), the shared movement (`bg_*`), the game module, cgame, qcommon and the codec.

Target of the gameplay: the game plays as the 1.01 server did at its default 20 Hz (the balance the game was tuned on: saber damage per swing, force power timings, weapon timings), at any tick rate, except where the owner decides a change (section 4). What changes is precision and latency: movement in identical 8 ms steps for everyone, the world drawn about 11 ms behind the newest snapshot instead of about 53 ms, hits judged against what the shooter saw.

## 1. How the engine works today (what the model replaces)

The model of Quake 3, kept by Jedi Academy:

- **The client makes one user command per rendered frame** (`CL_CreateNewCommands`, `client/cl_input.cpp:1386`), stamped with the time the client is drawing the world at (`cmd->serverTime = cl.serverTime`, `:1264`), which is about the round trip plus the interpolation delay behind the server's clock. The command's movement lasts from the previous command's time to its own: a frame of 8 ms at 125 fps, 3 ms at 333 fps. Movement therefore depends on the frame rate (the "125 fps" and "333 fps" jumps).
- **The server runs each command when its packet is processed**, before the next server frame (`SV_UserMove` and `SV_ClientThink`, `server/sv_client.cpp:1232-1329`, `:1210`; `ClientThink_real` and `Pmove`, `game/g_active.c`, `game/bg_pmove.c:11171`). Each client moves in its own time, behind the server's clock by its latency. A dedicated server runs each packet as it arrives: it waits for the next frame in `select` on its socket (`NET_Sleep`, `qcommon/net_ip.cpp`), which returns when a packet comes, and `NET_Event` runs it at once (`Com_Frame`, `qcommon/common.cpp`). (Corrected on 12 November 2026: this line first said the socket was drained once per frame; the audit of [step-14-audit-100hz.md](step-14-audit-100hz.md) section 5, S2, showed otherwise.)
- **The server frame** (`SV_Frame`, `server/sv_main.cpp`) runs the bots' AI and commands once (`SV_BotFrame`), then `GVM_RunFrame` once per `1000 / sv_fps` ms of elapsed time (several in a row after a stall), then the snapshots. `G_RunFrame` (`game/g_main.c:2919`) moves missiles, items and movers, runs every entity's think, and for every client runs the force powers and the saber once per frame (`WP_ForcePowersUpdate`, `WP_SaberPositionUpdate`, `WP_SaberStartMissileBlockCheck`, `g_main.c:3316-3318`, `:3343-3345`), then `ClientEndFrame`.
- **cgame predicts the local player** by replaying, every rendered frame, every command since the newest snapshot's player state (`CG_PredictPlayerState`, `cgame/cg_predict.c:1092-1100`), and draws the other entities interpolated between two snapshots, except the players with `cg_smoothClients 1`, extrapolated from their last command time (`game/bg_misc.c:2912-2935`, `cgame/cg_ents.c:3086`).

## 2. The target model

As Valorant, Overwatch and Rocket League (11 section 11.6):

**Time.** Tick `n` is the game time `n * 8` ms. The constant `TICK_MSEC` (8) replaces the `sv_fps` cvar; every clock stays in whole milliseconds, so `level.time`, `serverTime`, `commandTime`, `trTime` and the timers keep their meaning and their type.

**Server loop.** At each tick: read every packet that arrived (stamped with its arrival time), put each client's commands into that client's input buffer by tick; run, for every client in the game, the command of this tick (the last one received is repeated when it is missing, as Valorant and Rocket League do; a command for a tick already run is dropped); run the bots' command of the tick; run `G_RunFrame`; send a snapshot to every client; sleep until the next tick. Packets are read when they arrive, not once per tick, so their arrival time (the ping, the input margin) is exact.

**Client loop.** The client runs ahead of the server by about half the round trip plus a small margin, so that its command for tick `n` reaches the server just before tick `n` runs. It makes one command per tick it crosses in a rendered frame (one every 8 ms, whatever the frame rate), sampling the input of that frame; the mouse turns the view at once, every frame, and the command carries the angles at the tick. Each packet carries the commands of the last few ticks (the redundancy of step 11). The server reports in each snapshot how early the client's commands arrive (the input margin); the client runs its ticks slightly faster or slower (a few percent, as Overwatch's 16 to 15.2 ms and Rocket League's 2.5 %) to keep that margin small but positive.

**What the client draws.** The local player is predicted tick by tick from the newest acknowledged player state through the commands not yet acknowledged; between two ticks the view is either interpolated between the last two predicted ticks or advanced by a partial step (decision D5). The other players and entities are interpolated between snapshots at the delay of step 11 (about one interval plus the jitter: about 11 ms at 125 Hz), never extrapolated (`cg_smoothClients` removed; extrapolation stays only to bridge a lost snapshot).

**Commands.** A user command carries its tick (as `serverTime = tick * TICK_MSEC`, so `Pmove` keeps its arithmetic and always moves 8 ms) and the time the client was drawing the other entities at (the view time, for lag compensation). Both are close to the previous command's, so they cost little in the client packet format (step 8).

**Lag compensation.** The server keeps, for every tick of a bounded window, what a hit test needs from each player: position, box, angles, the animation state the skeleton is built from, and the states that change a hit (crouching, dead, saber state). A hitscan shot is traced against the players as they were at the shooter's view time (interpolated between the two stored ticks around it), after checking that time against the cap; the players are moved back only if a coarse test says the shot can reach them (Overwatch's volume). The saber and the force powers follow decision D2.

**Snapshots and bases.** One world state per tick shared by all clients (each client's snapshot is a list of entity numbers plus its player state), instead of each client's own copy of every entity in every frame; the same per-tick store feeds lag compensation (decision D3).

## 4. Decisions for the owner

Each with options, costs and a recommendation; the owner decides.

Owner's answers (11 November 2026): **the move to 125 Hz must not make saber combat block more or deal more damage** (a general rule: hits, blocks and damage per swing as at 20 Hz; the tests of part 2 compare both); D1, D3, D4 and D7 accepted as recommended; D6: (a), the models stay loaded at the first scoreboard (`cg_deferPlayers` kept); D5: (b), the partial step for display ("never less responsive; as precise and responsive as possible, more than now where feasible"); D2: (a) as revised below, no lag compensation for the saber and the force powers, compensation for the hitscan shots, (b) behind a cheat-protected debug cvar. Every decision is taken. Later the same day, after the first measurements: a few percent fewer saber against saber blocks than at 20 Hz (about 6 % measured with bots) are acceptable, even welcome (servers are "block land" today, sabers block far more than 15 or 20 years ago); damage must not grow; precision is preferred to an exact copy of 20 Hz, with tuning where a count moves too much.

- **D1. Saber damage at 125 Hz.** (a) The 20 Hz behaviour exactly: blade sweeps and damage on a 50 ms grid whatever the tick (what base_entranced does; no gain in saber precision); (b) the blade traced every tick, swept between ticks, with damage per swing and per victim defined in time (a victim hit by a swing is wounded once per swing, or once per 50 ms window of contact, to keep the 20 Hz balance); (c) a new hit model. Recommendation: (b) with "once per 50 ms window", which keeps the balance and uses the precision.
- **D2. Lag compensation of the saber and the force powers.** (a) None: the attacker hits what the server sees now (today's behaviour, the attacker aims ahead by their latency); (b) the defenders' bodies rewound to the attacker's view time for blade-against-body contacts, blocks and parries judged at the server's time with defensive moves having priority (as Overwatch's evasive abilities and For Honor's delay on attacks); (c) everything rewound, blades included. Recommendation, revised after the owner's rule that 125 Hz must not make the saber block more or deal more damage: (a) for the saber and the force powers (today's balance between attacker and defender; (b) lets more hits through, so more damage in practice), lag compensation only for the hitscan shots; (b) available behind a cheat-protected debug cvar to compare in game.
- **D3. Snapshot store.** (a) Keep the per-client copies and raise `PACKET_BACKUP` (558 MB at 32 players for 1 s); (b) one world state per tick shared by all clients plus a list of entity numbers per client snapshot (about 20 to 70 MB for 1 s at 125 Hz depending on the entities in use, plus 6.4 MB of player states), also used by lag compensation. Recommendation: (b), window of 1 s (128 ticks): a round trip up to about 900 ms keeps a base.
- **D4. Server commands.** (a) Keep step 10's rule and fix the cause found by the counters of S5; (b) a reliable channel: each command sent once, resent only when an acknowledgement bitfield shows its message lost, the client reordering what arrives. Recommendation: (a) first, (b) if the counters show the design itself is the cause.
- **D5. The local player between two ticks.** (a) Drawn interpolated between the last two predicted ticks (0 to 8 ms of added visual delay, nothing guessed); (b) advanced by a partial step of `Pmove` for display only (no delay, one more `Pmove` per frame, may differ from the next full tick). Today the client predicts up to the exact time of each frame (one command per frame), so (a) would add 0 to 8 ms (4 ms on average) to the local player's position compared with today, and (b) keeps today's responsiveness. Unity Netcode for Entities does (b): each frame it rolls back to the last full tick and predicts one partial tick with the remaining time; one-off actions (sounds, effects, spawns) run only when a full tick is predicted for the first time (primary: Unity, "Introduction to prediction"). Recommendation, revised: (b), with the events of a partial step never played. Other engines mostly draw (a): Glenn Fiedler's "Fix Your Timestep!" (primary) interpolates between the previous and current physics states, which trails by up to one step; the Netick engine's documentation interpolates the local player between its predicted snapshots (primary); Source is believed to do the same (not verified).
- **D6. Freeze when the scoreboard first shows unloaded players.** (a) Load a joining player's model at once (a short hitch when someone joins, the reason `cg_deferPlayers` exists); (b) load the waiting models while the local player is dead or spectating, when a hitch matters less; (c) load one model per frame in the background as soon as a player joins. Recommendation: (c), measured.
- **D7. Lag compensation cap.** Published values 200 ms to 1 s; Overwatch stops at about 220 ms of round trip. The rewind is the round trip plus about 11 ms. Recommendation: 250 ms of rewind (round trip up to about 240 ms), measured in game.

## 9. Part 2, final design: the game's logic at its 20 Hz pace on a 100 Hz tick (11 and 12 November 2026)

### Why the per-tick tuning was abandoned

Every saber against saber reaction (bounce, deflection, knockaway, broken parry, lock) needs `dmg > SABER_NONATTACK_DAMAGE`, where `dmg` is proportional to the blade's move in one server frame (`game/w_saber.c`). At a fast tick the move is a fraction of a 20 Hz frame's, `dmg` is nearly always 1 and attacks are no longer bounced: no coefficient restores it. The pain threshold rewrite (`P_RecentDamage`) was wrong (OpenJK already accumulates damage across frames until it reaches 10) and halved lava damage with its 750 ms debounce. And every bot measurement until then mixed the movement step with the server rate: the bots ran one movement step per server frame (`ClientThink` skipped `SVF_BOT`).

Owner's decisions (11 November 2026, evening): a tick of **100 Hz** (at 125 Hz, 50 ms is 6.25 ticks: thinks every 50 ms ran every 56 ms, the NPCs' 100 ms alternated 100 and 150 ms); the game plays identically to `sv_fps` 20 (damage, blocks, attack bounces, timings, AI), as precise as possible only where outcomes do not change; deterministic scenarios rather than free-for-all games as the proof; every audit claim checked in the code.

### What the code does

- Two clocks (`game/g_local.h`, `game/g_main.c`): `level.time`, read by all game code, is the logic clock, the last multiple of 50 ms; `level.tickTime` is the tick's time (bots' command times, the clamp of a command's time); `level.logicFrame` (`G_GRID20_STEP`) is true on the 20 Hz instants and on the first frame.
- On the 20 Hz instants, OpenJK's code unchanged: `G_RunThink`; per client and NPC in `G_RunFrame`: space, hacking, jetpack and cloak fuel, siege data, `WP_ForcePowersUpdate`, `WP_SaberPositionUpdate`, `WP_SaberStartMissileBlockCheck`; `ClientEndFrame`: powerups, `P_WorldEffects`, `P_DamageFeedback`; the level's rules; the bots' AI (`ai_main.c`, every 50 ms); all missiles (`G_RunMissile`), items (`G_RunItem`) and movers (`G_RunMover`: movement, pushes, crush damage, thinks; since 12 November 2026, owner).
- Every tick: the players' commands (movement with the command's time), the snapshots.
- The server's ghoul2 clock (`server/sv_main.cpp`) is the logic instant of the frame just run (`sv.time / 50 * 50`). The engine set it to `sv.time` after each game frame, so a frame evaluated the models at the previous tick's time while the game starts their animations at `level.time`: at 100 Hz the blades ran 40 ms ahead of their 20 Hz path, with identical player states; that made 5 times less saber damage in the first scenario runs.
- Missiles move only on the 20 Hz instants: with per-tick steps the engine's model trace (`server/sv_world.cpp`) gave other results (a step starting inside a player's box hits the box without a model test; one that leaves the box reports no model surface, so the hit location comes from the box), which changed hits, hit locations and damage (bryar 768 against 1,248 for the same 96 hits, homing rocket 48 kills against 0).
- Kept from the per-tick work: `fVSpeed *= 1.6f/20.0f` (G3, the value of `sv_fps` 20) and the mind trick window of 200 ms (`g_TimeSinceLastFrame` removed); both are OpenJK's values at 20 Hz.
- At `sv_fps` 20 every instant is a 20 Hz instant: the module runs OpenJK's code paths, and the same module at `sv_fps` 20 is the reference.

Price of identity: a saber contact or a missile impact is found at the 20 Hz instant after it, up to 40 ms later than a per-tick trace; the players' movement and commands are per command as before. Known limits: during the slow-motion end of a duel (`timescale`, `g_slowmoDuelEnd`, 0 on the owner's servers) the logic runs every 50 ms of game time. The movers moved every tick until 12 November; the owner chose the instants (exact identity); a free-for-all batch after the change: damage -1.3 %, deaths -0.9 %, blocks -2.0 %, within the noise.

## 10. Part 3 (tick loop): design, and Linux and Windows aligned first (12 November 2026)

### Decisions (owner, 12 November 2026)

- `TICK_MSEC` (10) replaces `sv_fps` everywhere: engine (`SV_Frame`, `SV_FrameMsec`, the snapshot pacing of `sv_snapshot.cpp`, `svnetstats`), game module (`g_xcvar.h` declares `sv_fps` with a default of 40; `ai_main.c`, `g_svcmds.c`, a debug box in `w_saber.c`), client (the snapshot interval read from `sv_fps` in the server info, `cl_cgame.cpp:665`; `timedemo`'s 50 ms).
- Ticks scheduled to the microsecond on a monotonic clock (W2: whole milliseconds were ±10 % of a tick); Linux `Sys_Milliseconds` (`shared/sys/sys_unix.cpp`, `gettimeofday`) moves to `clock_gettime(CLOCK_MONOTONIC)`. Revised after reading the loop and measuring (12 November 2026, owner): W2 was overstated. The frame loop carries the remainder (`sv.timeResidual`), so the average rate is exact and an interval's error does not accumulate; what moves is when each frame starts: on Linux about 0.1 ms on average (step 11's send-time measure on the VPS), on Windows 0 to 0.5 ms, uniform, because `timeGetTime` changes at the timer interrupts (every 0.5 ms with `timeBeginPeriod(1)`; measured against `QueryPerformanceCounter` over 5,000 changes). The client's interpolation delay absorbs both. Done: Linux `Sys_Milliseconds` on `CLOCK_MONOTONIC` (the wall clock was a real defect: a step of the system time stopped the frames or ran up to 5 s at once); Windows keeps `timeGetTime` (2.8 ns per call, `QueryPerformanceCounter` 14.7 ns, `std::chrono::steady_clock` 20.5 ns, llvm-mingw clang; no visible gain to pay for); no `Sys_Microseconds` for now, `SV_Microseconds` serves where microseconds count (packet arrival times of part 4).
- Bots called every tick inside the tick loop; the per-command path of `bot_debugClientRate 1` (a command every 10 ms, run as a player's) becomes the only one and the cvar goes.
- The ping measured over the 256-message window that exists (W7, valid up to about 2.5 s of round trip instead of 320 ms).
- Server command repeats counted by cause in `svnetstats` (a new command while others are in flight, the carrier lost, the `2 × ping` timeout), measured in game with the owner (LAN and VPS), then the cause fixed (S5, W5, D4).
- After a stall the server catches up at most 250 ms (25 ticks); beyond that the game clock skips ahead and the clients follow the jump as after `map_restart`. Surveyed: Unreal Engine clamps a frame to 0.4 s (`MaxUndilatedFrameTime`, `AWorldSettings::FixupDeltaSeconds`) and its physics to 1/30 s or 6 substeps of 1/60 s; Unity to 1/3 s (`Time.maximumDeltaTime`, which also bounds the `FixedUpdate` calls per frame); Godot to 8 physics steps per frame; Bevy to 250 ms (`Time<Virtual>::DEFAULT_MAX_DELTA`); Glenn Fiedler's "Fix Your Timestep!" 250 ms; Quake 3 and OpenJK today 5 s for a dedicated server (`Com_ModifyMsec`). All primary documentation except Unreal's ini default (secondary).
- `map_restart` and a map load keep their three frames of 100 ms (identical to 1.01; the client follows the jump since step 11).

## 11. Part 4 (commands per tick): plan and progress (13 November 2026)

A command stamped with the time the client draws the world at (today) is behind the server's clock and runs at the next tick, as today up to 10 ms later; a command stamped with a future tick (4c) waits for its tick.

### Order of the players' commands within a tick (owner, 13 November 2026)

4a ran the players' commands from client 0 to 31 at every tick, so within a tick a low client number always moved and shot first (OpenJK ran each command on arrival: no client number was favoured). `SV_RunClientCommands` now runs the clients in rising order at one tick and in falling order at the next: of any two players each is first every other tick, also on the 20 Hz instants (every fifth tick, so their parity alternates). No cost in CPU, bytes or memory. Not changed: the bots run before the players, in the order of their numbers (their commands do not go through the input buffer; the scenarios' two bots keep their order, `golden: SAME`), and the saber and the force powers run from client 0 to 31 on the 20 Hz instants (`G_RunFrame`, OpenJK's order, kept for the identity with `sv_fps` 20).

- Server (`SV_RunClientCommands`, `server/sv_client.cpp`): at each tick every player in the game runs one command whose time is the tick's. The command of the tick is the one dated in it; its margin is the real time between its arrival and the tick. Commands dated before the tick came after theirs: no movement time, what they newly pressed (buttons, a jump, the generic command) goes into the next command run (D2), their margin is negative. - Client (`client/cl_cgame.cpp`, `cl_input.cpp`): the command clock `cl.cmdTime = cls.realtime + cl.cmdTimeDelta`. The commands are made on that clock (`CL_CreateNewCommands`); it starts on the drawn time at the first snapshot, follows a jump of the server's clock with the drawing clock, and never flows backwards (a clock set back holds until the time catches up). `netstats` prints how far ahead of the drawn time it is and the margins received.
- cgame: the engine's command of the frame (`GetUserCmd( current + 1 )`) carries the command clock as its time; `cg.cmdTime` is that clock when the player is predicted and `cg.time` otherwise. The local player is drawn between the last two ticks at `cg.cmdTime`. The audit of 4d, done here: the times the movement code writes with the command's time and cgame compared with `cg.time` are the weapon charge (`cg_draw.c`), the rocket lock (four places in `cg_draw.c`) and the zoom (`cg_view.c`), now compared with `cg.cmdTime`; the saber lock test before each predicted command uses that command's time, as the movement code does. The other time fields of the player state are set by the game with its own clock and compared with `cg.time` as before (behind the server by the trip and the interpolation delay, as in OpenJK).
- Side effect on the game, in every player's favour alike: the movement code's times and the game's are now on one clock on the server. Before, a weapon charge started at the client's past time and was measured against the server's present, so it was longer by the player's latency.

### 4c, first test in game and its defect (owner, 13 November 2026)

On a local server the player could not move for several seconds after connecting (the connection icon over its head, then moved to the spectators), then "Connection Interrupted", then the game played normally; `svnetstats` showed a lowest margin of -100,286 ms and 467 commands after their tick. Cause, in the first version of the client's rule: the server sent its last margin in every snapshot, measured again or not, and the client took each one as a new sample; when no command of the snapshot's tick was found it took the present `cmdTimeDelta` as the one the command was made with. After the first setting of the clock the same old margin, counted against the new clock, moved it again at every snapshot: the clock ran away, the commands were dated more than a second ahead and refused, the margin the server then reported moved the clock the other way without limit, and the client, whose command clock never flows backwards, made no command at all until its time was reset.

Fixed, engine only (no change of the library):

- The server sends a margin once, in the snapshot after its measure; the other snapshots carry `INPUT_MARGIN_NONE` (-128 on the wire, which no margin gives; `inputMarginValid` in the client's snapshot).
- The client finds the command a margin is about by the snapshot's serverTime (the tick just run), not the player state's command time (which does not move while the player's commands do not run), and takes no sample without one.
- After the clock is set at once, the margins of the snapshots before the first command made on the new clock are left out (`cmdSettleTime`).
- The clock is set at once only while the window has fewer than 8 slots and the target is more than a tick away, or when it is more than 100 ms away; a sample more than 100 ms later than the window's median is not taken once the window is filled (an interruption, as for the drawing clock), and the windows' slots now expire with time even when no sample comes, so a link that really changed sets the clock again after the window's length.

### A move of -128, done after 4c in its own commit (owner, 13 November 2026)

A user command's `forwardmove`, `rightmove` and `upmove` are signed bytes. The keys give -127 to 127; `ClampChar` (`shared/qcommon/q_math.c`) lets -128 through for the sums of mouse or joystick movement, and a modified client can send it. OpenJK's server turned -128 into -127 when it read a packet (`qcommon/msg.cpp`, `MSG_ReadDeltaUsercmdKey`); since plan step 8 the packets come through netcodec, which gives the values exactly, so that rule was lost without a decision ([../09-changes-from-openjk.md](../09-changes-from-openjk.md) section 2, the row "A move of -128": "exact"). With -128 a player moves back, left or down at 128 / 127 of the speed (`PM_CmdScale`), 0.8 % more than forward, right or up. Owner's decision: -127 everywhere. To do: the client bounds the three moves to -127 to 127 when it makes a command, so that its prediction and the server use the same value; the server turns -128 into -127 when it receives a command (`SV_UserMove`), so that a modified client gains nothing; the row of 09 corrected. Engine only, no format change. Done at the source (owner): `ClampChar` (`shared/qcommon/q_math.c`), used only to bound a user command's moves (keys, mouse and joystick sums, in the multiplayer and the single-player clients), now bounds to -127 to 127 instead of -128 to 127; `SV_UserMove` (`server/sv_client.cpp`) still turns a -128 it receives into -127, since the server does not trust a client. The bots' commands (`ai_main.c`) and the movement code's own (wall runs, vehicles) already use -127 and 127. Built with clang; not tested in game (a -128 needs mouse strafing, a joystick or a modified client).

### 4d, first part (13 November 2026): a defect of the error check, and the cost measured before a cache

Read before writing the cache:

- The plan's figures for 4d (about 1,500 movement steps per second at 125 frames per second and 11,000 at 333, at 100 ms of round trip) were for a command per frame. Since 4b a frame replays (round trip + interpolation delay + margin) / 10 ms commands: about 12 at 100 ms, so about 1,500 steps per second at 125 frames per second and 4,000 at 333; a cache that replays only when a snapshot arrives would run about 1,300. The gain is at high frame rates and high pings only.
- A cache is not free of effects. The replay writes back, for the other players, the animations and the saber lock frame the local player's commands give them (`cgSendPS`, the end of `CG_PredictPlayerState`), and a snapshot becoming current overwrites them: without a replay in that frame they would show the snapshot's values until the next snapshot arrives, so a cache must also replay then (about 200 replays per second: no gain at 125 frames per second, about 40 % at 333) or handle the saber lock apart. And a replayed command collides with the other players where they are drawn in the frame of the replay: with a cache, at the arrival of a snapshot only.
- So the cost was measured first: a temporary command, `predictstats` (cgame), printed, since its last call, the frames that predicted, the movement steps run (per frame and per second) and the share of one core the replay took (the processor cycles of the replays over those of the frames, from the engine's precision timer, which counts on Windows only; its first version summed whole milliseconds and printed 0.00 %: a frame starts as the millisecond changes, so a replay never crosses one).

A defect found on the way, from 4b, fixed: the prediction error check (the state this frame computes for the last frame's newest tick against the last frame's own, which prints "prediction error" with `cg_showmiss` and feeds the smoothing of `cg_errorDecay`) sat before each replayed command, so it needed a command after the last frame's newest. With a command per frame there always was one; with a command per tick, a frame that brings a snapshot and no new command (1 in 5 at 125 frames per second, 2 in 3 at 333) had no check, the correction was applied at once without smoothing and `cg_showmiss` did not print it. The loop now takes one more turn after the newest command, for the check only. Expected in game: more "prediction error" lines than before at 333 frames per second for the same play (they were hidden), and corrections smoothed as at 125. Tested in game by the owner (13 November 2026, 125 and 333 frames per second on the VPS, with the build that still had `predictstats`): nothing wrong seen.

Measured in game (owner, 13 November 2026, the VPS at a ping of 21 ms, MSVC client, about 100 s each):

| | movement steps per frame | per second | share of one core | per step |
|---|---|---|---|---|
| 125 fps | 2.8 | 350 | 0.27 % | about 7.7 us |
| 333 fps | 2.4 | 807 | 0.51 % | about 6.3 us |

From these, computed and not measured: at 100 ms of round trip about 1.2 % of a core at 125 frames per second and 2.5 % at 333; at 300 ms about 3 % and 7 %.

Decision (owner, 13 November 2026): **no prediction cache**. The replay costs under 1 % of a core at usual pings, while a client already uses a whole core to draw at 333 frames per second; a cache would gain only above about 100 ms of round trip at a high frame rate, for more code and the changes of behaviour above. Part 4d is the fix of the error check. `predictstats` is removed once it has measured (it timed every frame and left an allocation at each map load); what the other statistics commands cost (`svnetstats`, `netstats`, `gamestats`) is to look at later (owner).

## 12. Part 5 (the snapshot store, D3): plan and progress (13 November 2026)

### What it is for

Nothing for the delay or the responsiveness of a player at a usual ping. It is for: the players above 290 ms of round trip, or in a burst of loss that long, whose snapshots are sent whole and in fragments once the base is refused (B1); the server no longer restarting after about 2.3 h on one map (B2); memory; fewer copies per tick on the server (part 7); and the store by tick that lag compensation reads (part 8), the main reason for its place in the plan.

### Plan (owner, 13 November 2026)

| sub-part | content | check |
|---|---|---|
| 5a | the server keeps one copy of an entity's state while it does not change (first written: one copy per tick), shared by the snapshots that hold it; a client's snapshot is a list of positions in the ring; the ring's counter on 64 bits; the window still 32 messages | the same bytes sent: the library's hashes, the 40 scenarios, `svnetstats` in game |
| 5b | the window 128 messages on both sides (`PACKET_BACKUP`, `eng::kPacketBackup`: the client must hold as many snapshots as the server may take as a base) | a base kept up to 1.25 s of round trip; memory measured |

Window (owner): 128 messages. Computed from the structures' sizes (532 bytes per entity state, 1,552 per player state): the server about 87 MB at 32 players (143 MB today), the client about 18 MB (4.5 MB today); 256 messages (2.53 s, the window of the acknowledges, the ping and the commands) would be about 174 MB and 35 MB: no player is playable above 1.25 s of round trip.

### 5a written (13 November 2026)

- Checked first: an entity's state is the same for every client of a tick (`SV_BuildClientSnapshot` copies `ent->s` as it is), and every snapshot of a tick is built in `SV_SendClientMessages`, after the game frame; a snapshot built elsewhere (a client entering, the server shutting down) is a tick of its own.
- Library (`codemp/netcodec`, full validations): a snapshot's entities may be given as an index, entity i being state `index[i]` of the ring instead of state `first + i` (`EntityRing::index` in `codec.h`, `Frame::index` in `engine.h`; the encoder's `SnapshotReader` in `message_codec.cpp` follows it; the decoder keeps its `RingReader`, which reads runs only, and refuses an indexed base). `Frame::firstEntity` and the `nextEntity` of `ServerCodec::Encode` are 64 bits; with an index, `firstEntity` is the oldest state the snapshot refers to, for the test that it is still held. ### The measure: `predictmiss`

Until now `cg_showmiss` compared the position and the two animations only. The cgame command `predictmiss` (`cgame/cg_predict.c`) compares, for every snapshot whose command time the client had predicted, the whole player state the client predicted for that tick with the server's, 32-bit word by word, and counts the words that differ; it counts nothing until its first call, and each call writes `predictmiss.txt` and starts again (its first version printed to the console). `tools/predict/ps_fields.sh` names the offsets (the layout of `playerState_t` from the compiler: 388 words). A word that differs is a field the server sets outside the shared movement code, or computes otherwise, or does not send: every cause of a prediction error is in that list, next to the fields the client is not meant to predict (health, events from the game, ...), to sort by hand. Built with clang; not run in game yet.

### Read in the code, not measured yet

- **The player state is not sent whole**: of its 388 words, 187 are not in the field tables (`data/fields.json` against the compiler's layout), and the snapshot holds 0 for them. Each frame the client predicts again from the newest snapshot, so the movement code starts from 0 in those fields at every snapshot, where the server's carry on. Those the shared movement code reads (`game/bg_pmove.c`, `bg_saber.c`):
  - `fd.forcePowerDebounce[FP_LEVITATION]` (`bg_pmove.c`, the force jump): during a force jump the server drains 5 force points every 300 ms (200 ms under level 2); the client, from 0, drains them at the first tick it predicts after every snapshot, so its force is 5 points under the server's for the whole jump;

### The commands made at the tick's start (owner: yes, 14 November 2026)

Owner: the client is for every player, at 100, 125 or 333 frames per second and more; a gain is judged over all of them, not on one setup. Made at the frames, a command reached the server 0 to a frame's length after its tick began on the command clock, and that clock had to run as much earlier: a key waited about 5 ms more at 100 frames per second, 4 ms at 125 and 1 ms at 333, so the delay of a key depended on the frame rate, against the rule that no player is favoured.

Written:
- `Com_Frame` (`qcommon/common.cpp`): the wait for the next frame also ends when the client's command clock enters a tick (`CL_NextCommandMsec`: the time left, read at the present time since `cls.realtime` moves once per frame; -1 outside a game, in a demo, in a pause, or across a jump of the clock), and the input alone then runs, `CL_InputTick` (`client/cl_input.cpp`): the system's events (`IN_Frame`, `Com_EventLoop`), the key binds (`Cbuf_Execute`, skipped while a `wait` command counts frames: `Cbuf_Waiting`), the view's turn, the tick's command and its packet (`CL_MakeAndSend`, the body of `CL_SendCmd`), without drawing. Not with a scaled or a fixed time (`timescale`, `fixedtime`). The frames still make the commands that are due when they run (a tick that begins while a frame is drawn, a frame rate with no wait).
- The input code measures on a clock of its own (`s_inputTime`: the frame's time, or the present at a tick between two frames) instead of `com_frameTime`: the keys' held time (`CL_KeyState`), the time since the input was last read (`frame_msec`: the keyboard's turn, the mouse's acceleration) and since the last command.
- Within `CL_InputTick` the client's clock (`cls.realtime`) is set to the present and put back: the packet's send time and the command clock are then exact, and the frame that follows moves the clock by its whole length as before.
- The dedicated server has the two functions as stubs (`null/null_client.cpp`).
